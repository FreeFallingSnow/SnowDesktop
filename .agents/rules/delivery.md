# Git、Issue 与发布

分支、双语提交和远端授权的日常底线见 [根规则](../../AGENTS.md#分支与提交底线)。涉及本文件任一操作时先读对应章节。

## Pull Request 与独立仓库

- 主项目维护者变更整合到当前 `release/vA.B.C.D`；没有合适版本分支时根据下一版本创建。外部 PR 若以 `main` 为目标，优先协助改目标；已经整合进版本分支时可按授权关闭原 PR 并说明整合位置，提醒后续不直接面向 `main`。不为规范改写贡献者原提交，补充修正独立提交。
- `website/` 与 `SnowDesktop_SteamAssets/` 只保留各自 `main`，日常内容/资产直接在其 `main` 整理提交，不留下 `release/*`、`codex/*` 等分支。清分支前核对远端、工作区和提交包含关系，确认要保留的提交均在 `main` 后才删本地与远端分支。
- 独立仓库推送前读取最新远端 `main`，优先正常推送；确需改写时确认不会覆盖他人新提交且保留内容已纳入，仅用 `--force-with-lease`，禁止盲目 `--force`。网站部署还须按 `website/AGENTS.md` 完成备份、构建、部署、线上核对；商店文案另行导入 Steamworks。

## 提交规范

摘要简洁、具体、不以句号结尾；中英文事实范围、限制及未验证状态一致。提交只描述实际包含的改动和已达到的验证。非平凡变更使用以下正文结构；示例中的命令及数字须换成真实记录。

```text
中文：
- 改动及影响范围

English:
- Change and impact

验证 / Validation:
- 实际命令及结果 / Actual commands and results

限制 / Limitations:
- 已知限制与未运行原因 / Known limitations and reasons for checks not run
```

纯文档、注释或无需完整构建时记录实际检查及未运行原因。没有限制可省略限制段，不虚构验证。

### 版本开发提交

格式：`<type>(<scope>): <中文摘要> / <English summary>`；scope 可省，使用稳定简短模块名，如 `dock/widget/build/release/l10n`。

| type | 适用范围 |
| --- | --- |
| `feat/fix/perf` | 提交本身含最终改动，提交前已完成功能验收、缺陷复现与修复验证，或性能测量 |
| `refactor` | 不改外部行为的重构 |
| `test/docs/build/ci/chore` | 测试、文档注释、构建依赖、CI 或其他维护 |
| `try` | 已编译成功、目标场景待验证的独立尝试 |
| `verify` | 对已有尝试完成实际场景验证，记录通过或失败证据 |
| `revert` | 撤销，正文注明被撤销哈希与原因 |

- 每次编译成功的代码尝试在下一轮修改前独立提交，不压成一个；编译失败状态继续修改到成功才保存。`try` 首行必须同时含“编译通过，待验证”和 `build passed, validation pending`，例如：

  ```text
  try(icon): 调整图标加载（编译通过，待验证） / Adjust icon loading (build passed, validation pending)
  ```

- `try` 正文写通过的编译命令、实际测试、未运行的目标场景及已知限制；只编译定向目标须写目标名，不能称完整 Release 通过。视觉、交互、兼容性尚待实际验证时使用中性表述，不写“已修复 / fixed / resolved”。
- 纯组件更新的 `try(widget)` 首行使用“组件验证通过，待实机验证”和 `widget checks passed, runtime validation pending`；正文记录组件检查、标准构建或手动临时同步、待实机与限制。手动同步不能声称宿主编译通过。
- 后续无代码修改的验收创建独立 `verify`，允许空提交，记录对应 `try` 哈希、步骤、结果和证据。失败也如实记录，再由后续 `try` 保存下一次成功编译；不改写历史 `try` 伪装当时已验证。
- 缺陷关联用 `Refs #编号` 或完整 Issue 链接，关闭条件满足前不用 `Fixes/Closes/Resolves`。

### main 版本提交

唯一版本提交格式：`vA.B.C.D - <中文简要更新> / <Brief English update>`。摘要只概括该版最重要且已验证的用户可见变化，不加 Conventional Commit 前缀、不罗列内部实现。正文按中文、English、验证列主要更新和发布检查。将用作 Squash 默认标题的 PR 在合并前改为该格式。

## Bug 与 Issue

- 用户反馈、已发布问题，以及需后续跟踪、跨模块、多轮尝试或实机验证的 Bug，在官方 GitHub Issues 跟踪；聊天、Commit 和本地日志只作证据。开发时当场消除的临时编译错误和调试中间状态不逐项建档。
- 修复前检索已有 Issue，核对现象、触发及影响。同问题沿用稳定编号，补充反馈和多次尝试并入原项；独立修复/验证/发布的问题分别建档并关联。
- 正文记录现象、预期、复现、应用版本或 Steam Build ID、渠道和环境、影响、证据、关闭条件。未知项标待补，区分已复现、代码推导风险和待确认反馈，根因结论附相应证据。
- 创建、评论、更新、关闭须有远端授权；缺少授权或远端不可用时在忽略的任务目录留可补录草稿与证据，说明尚无编号，继续独立排查。编号和远端状态按实际回执记录。
- 每项未关闭问题有当前状态与下一步，优先复用标签/看板；缺少字段就在正文记录，不为单次修复建立新体系。

| 状态 | 记录重点 |
| --- | --- |
| 待复现 | 反馈/风险证据、缺少的环境输入或触发条件 |
| 已确认 | 复现步骤、结果、影响及处理版本 |
| 处理中 | 方案、分支/提交和剩余问题 |
| 待验证 | 候选提交、实际检查、目标场景步骤和待验项 |
| 待发布 | 目标场景结果、渠道、测试分支版本或 Build ID |
| 已关闭 | 关闭原因；修复关闭提供验证及实际交付版本/Build ID |

- 编译成功但目标场景未通过保持待验证；失败记录步骤、证据和候选，再继续尝试。
- 修复关闭须同时满足关闭条件、目标场景通过、已进入报告者所用发行渠道；记录步骤/结果/提交/交付版本，Steam 再记分支与 Build ID，同版本多次更新按实际构建区分。
- 正式用户的修复交付以 `public` 实际生效为准；测试验证完成而正式版未发保持待发布，证据按下节核对。推送与发布按用户授权执行。

  > 例如，`internal-dev` 已验证的 Build 后续提升到 `public`，须取得 public 回查证据后再关闭正式用户的修复 Issue。

- 重复、预期行为或明确不处理可说明依据后关闭，重复项链接主项。未复现、等补充或验证失败不能作为修复关闭理由。同问题仍存在时重开并补实际构建证据，不同根因另开关联项。

## 本地版本整合与发布

1. 在版本分支完成全部功能/修复/资源、最终标准 Release、应用全量及核心实机验收，记录候选源码与运行身份、结果和失败。最新标准构建的源码/工具链/产物身份匹配时复用，仅补缺失或失效测试目标；不匹配则说明并重建受影响目标，不能以旧产物充当最终候选。
2. 通过 `scripts/squash_release_to_main.bat` 本地压缩合并，确保 `main` 每版只新增一条版本提交，并在该提交创建与 `version.json` 一致的本地注释标签 `vA.B.C.D`。不普通 merge 引入全部开发历史。
3. squash 后只核对版本提交、标签、文件树、发行包和用户在本地 `main` 的实际测试。发现问题回版本分支修正、构建、验收后重新生成本地版本提交及标签，不在 `main` 追加修复/验证。
4. **用户检查并测试本地 `main` 后，明确决定是否推送。** squash 脚本只允许本地分支/提交/标签，严禁 fetch/pull/push/远端 API/删分支；参数或环境变量不得放开此限制。
5. `scripts/release.bat` 无参数为人工 TUI、有命令参数为非交互 CLI，两者复用 `scripts/release_manager.ps1`。远程动作与本地 squash 分开；用户测试后，以交互版本确认或 CLI `-Yes -ConfirmVersion A.B.C.D` 推送远端 `main` 和标签。
6. 所有发行包、校验、说明、状态、日志位于 `artifacts/vA.B.C.D/`。版本完成发布后停用旧版本分支，下一版从最新 `main` 创建。

### GitHub Release

- 标题仅为 `version.json` 原始号，如 `1.0.6.0`，不加产品名、`v` 或摘要。正文先 `## 中文`，水平分隔线后 `## English`；主题分组用 `###`，中英文事实一致。正文不重复产品名/版本大标题、不删已确认用户更新、不写开发过程或“已知问题”章节。
- 历史格式整理仅按授权改正文，保留原事实与附件，写前后核对线上内容。用户已手动修正线上 Release 时只读核对，不自动覆盖或补回已移除附件。
- 默认公开附件仅便携 ZIP 和对应 `SHA256SUMS.txt`；未签名 MSIX、本地自签测试 MSIX、`.msixupload`、`.appxsym` 不默认公开。公开分发另须有相应授权。
- 公开校验清单在版本目录 `github-release/` 单独生成，只列实际上传文件；版本根保留全部产物清单。发布后核对线上标题、附件集合及哈希。

## Steam 正式更新基线

1. 查询 Steamworks 分支或用 SteamCMD 刷新 app info，读取目标 App ID 的 `public` 实际 Build ID，记录查询时间、App ID、Build ID 和原证据路径。同版本可多次正式更新；私有分支状态使用其可取得的有效记录核对。
2. 精确匹配成功 SteamPipe 回执或发布记录，核对分支、Depot Manifest ID、包清单 `runtimeBuildId`、哈希及打包时 `sourceCommit`。测试 Build 提升到 public 须有提升记录或之后的 public 回查。
3. 用户指公开公告时，把公告时间与 public 生效记录对应；记录须能唯一对应构建和源码，存在歧义时报告不确定项。
4. 以已发布源码提交（不含）至目标提交（含）比较，分别标明正式、测试分支、未发布及未提交内容。

### 面向用户的更新说明

- 按用户上次实际正式构建归并开发提交，只写可感知的新功能，以及上次正式版确有、此次已验收修复的问题；同版本号也按实际 Build 比较。
- 从用户可执行操作、可见变化和不再遇到的问题表述，不写内部技术/流程、构建测试、日志、分支提交，也不写发布前已消除的临时问题；草稿及翻译范围一致。
- Steam 公告每种语言标题最多 80 字符，按 JavaScript `String.length` 计数（含空格标点）。CSV 生成器逐语言拒绝超长；先缩译文、不直接截断，交付前重读最终 CSV 核对标题长度、语言集合和列顺序。
- 小幅更新标题默认直接写可见变化，不带版本号或“小更新：”前缀；用户另有要求时遵从，不改变 GitHub 标题及 Git 版本格式。

### 每次 Steam 生效的 Git 记录

- 实际设为 `public` 或 `internal-dev` 生效后，各新增一条独立 Git Commit，即使仅提升已有 Build 也用空提交；预览、仅上传未生效或失败不记成功，不混入下轮源码、不改写发行源码提交。
- 记录在对应版本分支；已完成合并并停用时用 `steam/publication-log`，不在 `main` 新增第二条版本提交，也不自动推送记录分支。
- 首行示例：`chore(steam): 记录 public Build 25480127 发布 / Record public Build 25480127 publication`。正文中英记录生效时间、App ID、分支、Build ID、打包 `sourceCommit`、Depot Manifest ID、`runtimeBuildId`、包/清单哈希、发布与回查路径、实际验证及待验项。
- public 结论须有 public 回查或等价 Steamworks 证据；私有分支无法独立回查时，注明已核对的 SetLive 与成功回执及这一证据边界。
- 交付结果同时给新记录提交哈希与完整首行、被发布源码提交、Steam Build ID，分别标注发行源码与事后记录提交。

## SteamCMD 客户端恢复

- 首次登录前记录桌面 Steam 是否运行及实际 EXE 路径；集中完成所有需登录的上传、预览和查询。成功、失败、取消均在本任务 SteamCMD 全部退出后统一恢复一次，避免恢复后又登录替换会话。
- 原先运行时已获自动重启授权，无需再问，执行前简短告知；用记录的 Steam 路径 `-shutdown` 正常退出，有限等待后 `-silent` 启动，`Start-Process` 使用 `-WindowStyle Hidden`。不强杀进程树或游戏；原先关闭则不启动，用户后续明确保持关闭则遵从。SteamCMD 退出后按上述步骤恢复桌面会话。
- 恢复只读核对进程及本次重启后的连接日志，不再登录 SteamCMD。分别报告已重启、已在线；在线状态以新日志中的登录成功为准；退出受阻、重启失败或需 Guard/人工登录时报告实际状态与所需动作。

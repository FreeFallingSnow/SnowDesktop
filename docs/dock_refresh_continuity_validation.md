# Dock 刷新期间的归属连续性

## 原始反馈与原因

2026-09-21，用户在 `ddd7ae74` 启动异步化之后反馈：Shell 刷新时，固定区内已经运行的
程序短暂出现在运行区，随后恢复；文件区也有瞬间位置错乱。`291c17b8` 记录该实机验证失败。

刷新入口仍清空应用身份与文件夹分类缓存，异步查询在尚未返回时给出空结果。
`RefreshDockRunningWindows` 将这种暂时未知视为“不属于固定应用”，产生临时运行区项目；
`IsFolderDockEntry` 同样将未知视为普通项目，造成文件区重新布局。此前的启动耗时和
自动测试没有覆盖刷新与异步完成之间的状态，不能证明这两个交互已经正确。

## 改动与风险边界

- 固定应用身份、文件夹分类、映射文件夹系统图标在失效后保留最后一次确认值，同时后台重查。
  已完成的空结果与尚未完成的查询分开表示，真实的目标改变仍会更新匹配和区域。
- 缓存键包含逻辑引用和来源路径；来源文件戳、请求票据和刷新代数共同防止过期结果覆盖。
  已删除来源的缓存被移除，重新出现的同名来源不会接收旧请求。
- F5、Shell 完整快照、布局重载及重命名后的全局失效均使用同一保留规则；旧排队查询被取消。
  文件夹来源版本改变时，仅保留区域分类，暂不允许使用旧目标执行操作。
- 文件夹分类真正改变后重新规范 Dock 顺序。没有把快捷方式解析或图标查询移回 UI 线程。
  不修改公共组件 API、版本号、布局文件格式或用户数据。

缓存测试使用真实生产缓存和应用匹配规则，Shell 读取完成顺序由用例明确控制。
这些测试不模拟完整桌面宿主，也不能替代实际画面验收。

使用本次标准构建，在固定区已有运行程序、文件区已有文件夹/快捷方式的原始配置下：

1. 连续 F5 和桌面右键刷新，观察固定项目始终留在固定区，运行区没有对应重复项目。
2. 新建或修改一个无关桌面文件以触发 Shell 通知，观察文件夹所在区域及映射图标保持稳定。
3. 修改固定快捷方式的实际目标后刷新，等待查询完成，确认匹配确实切换到新目标。
4. 删除固定来源后刷新，再添加同名但目标不同的来源，确认没有恢复旧身份。

快捷方式实际目标变更、删除后同名重建的边界由本次自动回归覆盖，尚未收到逐项桌面反馈。
首次启动或首次添加的来源尚无已确认值时，仍需要等待首次后台识别。

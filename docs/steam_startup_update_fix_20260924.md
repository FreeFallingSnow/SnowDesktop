## 启动协议与兼容边界

- Steam 清单增加可选 `launcherProtocol: 1`，`schemaVersion` 仍为 1。打包脚本随新宿主写出该字段。
- 启动器创建随机共享状态与 Ready 事件，以挂起方式创建宿主、写入子进程 PID，再恢复运行。
  宿主验证通道身份，并清除环境变量，避免把本次身份传给帮助进程或崩溃重启进程。
- 实际宿主在 `wWinMain` 开始时就标记数据边界，早于部署检查、辅助命令、单实例与设置访问。
  因此自动恢复仅适用于创建进程、DLL 加载及进入宿主入口之前的失败；不声称能安全回退全部初始化失败。
- `DesktopApp::Run` 完成首帧和桌面接管后发送 Ready。启动器核对当前选择再确认、清理一次；保留前一个确认版本。
- 退出 0 或 `ERROR_CANCELLED` 不触发失败恢复，也不冒充 Ready。等待 60 秒超时保留慢启动宿主及运行目录，记录 1460，不强杀宿主、不自动降级。
- 新启动器遇到未声明协议的旧宿主仍可创建进程，但不伪造确认、不清理。新宿主没有通道时为空操作。
  旧启动器不识别新的确认语义，不能获得这些恢复保证；交付需要启动器、宿主及清单配套更新。
- `--snowdesktop-launcher-no-ui` 仅抑制启动器自己的错误弹窗，保留日志和退出码；用于维护/自动化诊断。
  `--snowdesktop-launcher-apply-only` 仍不启动宿主，并允许显式重试此前被拒绝的同一分发。
- 以上为安装与启动协议调整，不改变 Lua 组件公共 API，不提高组件 `apiVersion` 或 `minHostVersion`。

## 跨启动的数据保护

单次进程内的 DataAccess 状态不足以保护后续重试。本轮隔离复现：A 已确认，B 报告数据访问后退出 13；
随后同时损坏 B 载荷和分发清单，早期候选仍启动 A。宿主替身只模拟数据边界，不迁移真实用户数据。

最终实现增加 `.snowdesktop/launch-history.txt`：启动器在创建任何宿主进程前，以原子替换和刷盘保存版本身份及随机尝试标识。
这是一项保守记录，表示该版本**可能已经访问数据**，不是启动成功证明。规则如下：

1. 分发失败时只能尝试当前选择和最近启动记录，不能单凭 `confirmed-runtime.txt` 或 `previous-runtime.txt` 回到更早版本。
2. 观察到本次子进程在数据访问前失败，且选择和尝试标识未被其他启动替换，才允许恢复到本次启动之前记录的版本。
3. 同一版本并发启动也使用不同标识，较早启动的失败不能撤销较晚启动；找不到可信前驱时记录失败，保留目录与数据。
4. 恢复时先持久恢复数据边界，再记录失败清单摘要和当前指针。指针切换中断后，普通启动会排除失败摘要并修复选择。
5. 保存的前驱记录损坏时停止旧版本清理；其存在不再自动赋予跨数据版本回退资格。

相同替身和操作在最终启动器下返回 1603，未再次启动 A，A 的目录仍保留。
自动测试同时覆盖这一跨进程边界及同版本并发恢复；没有把真实文件操作、哈希、发布或 IPC 模拟掉。
本记录不保证人为替换状态文件、显式安装旧版本或外部启动旧 EXE 时的数据格式兼容。

## 加载器诊断

无效 EXE 的测试暴露了另一个阻塞：系统关键错误对话框可在进入子进程退出监测前阻塞创建调用。
隔离对照中，默认模式超过 6 秒未返回；直接继承 `SEM_FAILCRITICALERRORS` 后能记录错误 216 并恢复前驱。
最终仅设置该标志，不关闭 Windows 崩溃报告。
[Microsoft 的 SetErrorMode 文档](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-seterrormode)
说明了关键错误弹窗与子进程继承语义；
[CreateProcessW 文档](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)
说明创建成功早于 DLL 初始化结束，因而不能把创建成功作为宿主就绪证明。

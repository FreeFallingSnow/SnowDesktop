# SnowDesktop 测试规范草案

状态：**提案，尚未生效**。日期：2026-09-10。

依据：[上游规则、Skill 与现状调研](testing_policy_research.md)。本文件准备替换和细化 [AGENTS.md](../AGENTS.md) 中的测试相关条款；采用前以现行 AGENTS 为准。本文提出的依赖选择和结果缓存尚未实现，不能作为跳过现行必需检查的依据。

## 1. 测试的目标与证据边界

测试用于阻止具体的用户行为回归、公共 API 破坏、安全或数据不变量破坏、已知缺陷复发，以及低层无法保护的关键架构边界。不以测试条目数、断言数或统一覆盖率作为功能验收标准。

新增或改写测试时，至少能简洁回答：

1. 哪个生产故障会让它失败？
2. 它调用了哪个真实生产入口，哪些边界使用替身？
3. 预期结果来自哪项产品规则、数据不变量或独立样本？
4. 哪个可观察结果与非零退出状态能确认失败？

这些说明放入现有用例名称、短注释或评审说明即可，不为每条断言新增模板文件。没有独立风险收益的重复测试、格式检查和框架自身行为检查，应删除或改写。已有测试不能因标签名称或运行慢被批量删除。

## 2. 分层与登记

| 层次 | 适合证明的内容 | 不能单独证明的内容 |
| --- | --- | --- |
| 静态及数据契约 | schema、资源映射、本地化键、禁止依赖等稳定约束 | 对应代码实际执行、界面行为正确 |
| 规则与模块行为 | 生产规则函数、解析器、容器或事务的输入输出与不变量 | 宿主是否调用它们 |
| 生产链路集成 | 真实调度、内容读取、目标提交、存储等多个模块之间的连接 | 原始系统输入、实际焦点、视觉或特定环境兼容性 |
| 系统或实机验收 | 指定构建、输入来源和环境中的完整可观察行为 | 所有未运行的组合或环境 |

层次、业务域和运行条件应分别说明；一个标签不能同时代表它们。逐步补充元数据时继续以 `CMakeLists.txt` 和 `SnowDesktopTests` 为唯一测试登记来源，脚本从 CTest 清单解析目标，不在多个入口复制目标清单。

现有 `contract`、`integration`、`core` 等标签保留兼容性，先审计再调整。`fast` 排除环境集成测试，`core` 是已登记的子集；它们均不自动等于本次改动的最小充分集合。环境相关端到端测试继续标为 `integration`。

## 3. 按风险和阶段选择检查

### 3.1 日常开发与交付

下表是拟采用的规则。模块局部交付可免全量的条件是：其生产调用链、依赖及关键风险映射已经审查，且存在有效的全量基线。映射未完成的模块在交付检查点保持现行全量要求；开发过程仍使用定向测试。

| 变更或阶段 | 必需检查 | 全量触发方式 |
| --- | --- | --- |
| 纯文档、注释，不改变运行或生成结果 | 差异、链接及与内容相符的静态检查 | 无需宿主构建或全量 |
| 纯 Lua 组件包 | lint、相关组件测试、包校验；实机前核对实际加载来源 | 按现行纯组件规则，无需宿主全量；公共 API 或宿主变化另算 |
| 缺陷复现与普通开发迭代 | 能暴露本次故障的用例；改动后运行受影响的最小充分测试；原生改动完成匹配编译 | 不因每轮编辑、每次回复或中间 Commit 全量 |
| 模块局部改动的待验证 `try` | 定向规则及相关集成测试；交付程序按标准入口构建；列明实机待验证项 | 普通交互调校不重复全量；触及高风险边界按下一行 |
| 公共 API、跨模块行为、数据迁移/所有权/权限、OLE 生命周期、异步调度、构建或测试基础设施 | 定向复现及关键边界测试；生产代码按需标准构建 | 在本轮可交付改动稳定后运行一次全量；中途用定向结果定位，后续影响测试输入的改动需更新证据 |
| 已有完整风险映射的模块局部最终交付 | 所有受影响模块和连接边界的测试；原问题验收；说明有效基线和选择理由 | 无高风险触发且基线有效时可免全量；无法证明范围时升级为全量 |
| 测试源码局部调整 | 运行受影响条目；新增回归证明失败信号，删除说明覆盖替代关系 | 不改变公共运行器、选择器或清单机制时无需机械全量；测试基础设施变化仍需全量 |

本次外部拖放修改涉及跨模块执行和 OLE 异步生命周期，属于高风险。每轮先跑定向回归，稳定交付检查点全量；全量不能补偿缺少真实提交断言。

### 3.2 合入、发布与复用

| 检查点 | 拟采用要求 |
| --- | --- |
| 维护者 PR 合入版本分支或等价整合 | 对最终整合内容具备一次有效全量结果及受影响功能验收。相同输入的本地或 CI 结果可复用，无需两个环境无条件各跑一次。合入其他改动后重新判断证据是否有效 |
| 发布候选 | 标准 Release 构建、全量自动化及核心系统验收必须绑定最终候选源码、配置和产物；包装后另核对包内容、版本及安装/便携形态。不能仅凭测试二进制通过证明发行包可用 |
| 用户完成原场景验证后创建 `verify` | 记录验证对象和反馈，按变更风险及交付阶段补足检查。需要全量且已有有效结果时，不因新增验证记录再跑一次；只有定向结果或输入已变化时，补足所需范围。已满足局部交付条件的改动不因 Commit 类型单独升级为全量 |
| 同一候选再次汇报、提交文档或标记发布状态 | 复用仍有效的证据，明确其原始运行时间与对象，不伪装成本次新执行 |

“一次”指同一组有效输入的一次通过，不是整个任务无论改多少代码都只测一次。只改提交说明而输入未变不使证据失效；版本、资源、编译开关等实际输入变化必须评估。不能以“稍后会跑全量”作为当前已完成修复的依据。

### 3.3 当前可用入口

开发中明确选择范围，不依赖无参数默认全量。以下只是现有入口示例，不是一份新的测试目标清单：

```powershell
scripts/test.bat list
scripts/test.bat name 'slot|virtual_file_drop|url_drop_resource'
scripts/test.bat label 'storage|security'
scripts/test.bat core
scripts/test.bat fast
scripts/test.bat full
```

选择由改动及调用链决定。上面的拖放正则适合内容读取相关回归，并非所有拖放改动的固定充分集合；Shell 文件操作、落点、持久化等变化还需纳入对应测试。零匹配必须报错，不得记为通过。

本草案不改变现有无参数默认行为，也未新增命令。后续若修改 CLI 语义，须按公共 API 变更提醒规则单独说明兼容影响。

## 4. 验证结果的有效性

结果至少绑定以下输入，并保存命令、退出码、实际选择集合、配置和日志位置：

- 提交及未提交变更的内容；不能只比较分支名或版本号。
- 被测生产源码、测试源码、传递依赖、生成输入、组件与其他资源。
- CMake Preset、构建配置、编译器/SDK、依赖版本和影响行为的编译开关。
- 相关环境、权限、功能能力、组件来源；实机验收还包括运行产物及所用样本。

拟建立的记录以内容指纹判断输入一致性，产物使用哈希辅助追溯；不记录无关环境变量或凭据。结果分类为“本次执行通过”“引用仍有效结果”“失败”“未运行”“环境阻断”“待实机”，不得把后三种算作通过。

复用条件：前次已通过、无未解释的不稳定失败、相关输入及测试选择规则未变、日志可追溯。失败结果、来源不明的旧二进制或只有版本号的记录不能复用。用户要求重新验证或怀疑缓存判断失误时，允许强制重跑。

有经过验证的依赖映射时，变化只使受影响条目的结果失效；没有可靠映射时，不能凭“看起来无关”复用一个旧全量结论。实时网络或系统兼容性结果只证明当时的环境，不因代码相同永久有效。

基线全量加本次定向通过，应按这两个事实报告，不能改写成“本次完整测试全部通过”。人工实测也必须对应实际加载的宿主与组件；源码改好、复制成功和界面验证通过是不同证据。

## 5. 自动选择与耗时治理

当前阶段使用已有的 `name`/`label` 入口人工选择，并说明理由。后续自动选择器必须满足：

1. 从 CMake/CTest 登记与可用的构建依赖获取候选目标，再补充运行时资源和语义边界映射；不只按文件目录猜测影响。
2. 处理新增、删除、重命名、未跟踪输入、公共头文件、生成文件、清单和编译选项。映射缺失、基线不可用或分析失败时，明确报告并扩大范围，不能返回空集合通过。
3. 输出选择与排除原因，以及要求全量的风险触发项。目标只能解析自唯一登记源；业务风险映射不得成为第二份可执行目标清单。
4. 先以建议模式与检查点全量对照，不直接省略检查。用已知历史缺陷、受控变异和跨模块变更验证漏选情况；自动省略启用前记录验证范围及剩余盲区。

耗时应分别记录配置、增量构建、测试执行、产物校验和实机准备；积累中位数、较高分位耗时及失败发现情况后再设置预算。优先消除重复配置/构建、固定等待、重复断言和不必要数据量；只有共享资源已隔离时才扩大并行。

新框架、大规模变异或随机压力扫描应有独立收益与预算，不能无条件塞进每次迭代。关键确定性回归进入对应日常集合；成本较高的扩展扫描在合入、发布或专门运行阶段执行，并分别报告。

## 6. 缺陷回归与测试自身验证

缺陷修复应保留最小原始复现，并在修复前看到预期业务断言失败。编译错误、测试夹具路径错误、超时或环境故障不算成功复现；修复后用相同输入验证预期结果。

若实现已存在，可在隔离副本或专用测试接缝中暂时恢复错误行为，检查测试能否发现。不得覆盖用户未提交修改、回退整个工作区或为满足测试顺序删除已完成实现。

关键用例新增、漏测调查或断言改写时，选择一个与风险相关的错误变化，例如跳过目标提交、始终把图片保存为链接、提前删除来源。用例应因匹配的行为断言失败。完整变异扫描不要求每次提交运行；未执行到变异点、编译失败、超时或等价变异不得计为有效发现。

预期来自产品规则、独立的固定样本或独立判定方法；不得调用被测函数生成自己的期望，也不得复制生产算法后比较两个相同实现。属性测试应有非平凡性质、有效样本数和可复现失败输入，种子或缩减后的最小样本可进入回归。

## 7. 生产边界、替身与异步

测试替身适用于网络响应、系统失败、时间与完成顺序等外部边界。对真实业务链的声明必须保留真实调度、目标解析和提交逻辑；替身直接返回成功的目标处理器只能证明上游协议。

文件测试使用隔离临时目录和真实小文件，成功及失败均清理；不能操作用户桌面布局、真实业务文件或构建输出中的 `data/`。可控内存存储用于局部事务测试，真实持久化边界仍需自己的集成用例。

异步用例控制开始、完成、取消及刷新顺序，等待可观察条件并设置上限，避免依赖固定睡眠或机器速度。覆盖对象销毁、目标失效、重入、两个任务交错和部分失败。失败后重跑只用于诊断，不能消除首轮失败记录或自动变绿。

测试接缝优先放在内部依赖边界；不为方便测试暴露新的组件公共 API。确需改变公共接口时，仍遵守独立的兼容性提醒及验证要求。

## 8. 核心拖放验收要求

[全场景矩阵](drag_drop_validation_matrix.md)作为场景清单；每个场景必须有明确支持/拒绝语义、验证层、实际结果及未覆盖边界。规则组合数量不折算为实机覆盖数量。

| 维度 | 必须纳入的风险类别 |
| --- | --- |
| 来源与目标 | Explorer、Edge、内部桌面/Dock/各组件、外部导出；桌面及全部受支持槽位目标；同实例、跨实例、跨类型、禁止目标 |
| 内容 | 文件、目录、混合多选、快捷方式、虚拟文件、图片位图/HTML/URL、无扩展名图片、普通网页、本地文件 URL、混合格式优先级 |
| 操作 | 默认及修饰键复制/移动/链接；重排、引用绑定、替换、拒绝；悬停提示与最终执行一致 |
| 时序 | 同步/异步、读取延迟、取消、目标消失或改目录、批次部分成功、两次交错完成、刷新与重启 |
| 环境与边界 | 重名、Unicode/长路径/UNC、权限和网络失败、容量限制、DPI/多屏/跨页、组件来源与能力状态 |

产品明确支持的来源/目标关系都要进入清单，禁止关系也要有拒绝证据。已知缺陷及高风险交叉组合必须逐项验证；次要维度可按等价类或成对组合减少重复，但必须说明理由，不能删掉同步/异步、真实提交和失败保护等关键差异。

每次文件操作的验收至少检查：

- 源文件按复制/移动语义保留或移除；未成功项不误删。
- 目标文件的数量与内容正确，无意外覆盖、重复或临时内容残留。
- 组件身份、逻辑归属、插入位置正确，刷新或持久化后仍成立。
- 每次接受的释放对应一次有效提交，取消或拒绝不提交；异步完成及清理次数符合真实协议。
- 网络图片以实际可解码内容核验，不能只看后缀、MIME 或占位字节；普通网页和失败回退按各自语义核验。

DND-01 必须从带异步能力的外部输入进入实际宿主组件提交；DND-02 必须从原始图片内容进入正确目标，分别覆盖成功与回退；DND-03 必须控制两次完成与模型刷新顺序，检查每次落点独立。局部 helper 的红绿结果不能单独关闭这些完整场景。

桌面宿主的拖放、框选、Dock 悬停和视觉验收遵守现行限制：不使用 computer-use 或同类自动化发现、捕捉或操作该宿主，也不以启动应用、反复截图等方式绕过。使用稳定可观察的等价证据，或由用户验证原场景并记录反馈。设置窗口等独立可操作界面不因此被排除。

## 9. 源码契约与低价值测试的处理

源码静态检查只保护具体、稳定的负向约束或架构边界，并说明为什么较低成本的行为检查不能替代。归一化换行，避免依赖排版、局部变量名和无语义顺序。

搜索到函数名、线程声明或某行调用，不能宣称功能已经执行、执行在正确线程或没有阻塞。若注释中的文本能让一个宣称运行行为的测试通过，应改成生产行为测试，或收窄为它真正能证明的静态约束。

资源/schema/翻译键等数据契约仍可直接检查数据；它们保护的就是资源约束。是否读取文本不是取舍标准，断言与声称行为之间是否有有效联系才是。

对原有 117 个条目按“风险、生产入口、替身、独立预期、失败证据、耗时、处理意见”审计。处理意见限于保留、改写、合并、删除或记录暂时的环境阻断；优先处理核心路径和已知漏测。删除前确认没有丢失独立风险覆盖；暂时阻断必须有可追踪的恢复条件，不能长期算通过。

## 10. 交付记录与采用步骤

简单改动只需简短记录，不机械填满空表。涉及核心行为的交付至少包含：

```text
变更与风险：影响的用户行为、模块及边界
对象：提交/未提交内容、配置、实际宿主与组件来源
测试选择：运行哪些现有条目，为什么足够，是否触发全量
结果：实际命令、退出结果、范围、日志；新执行或引用旧证据
缺陷证据：修复前的正确失败、修复后的同场景结果
实际验收：原始样本及文件/状态结果，或明确待实机
未执行：未运行范围、理由与剩余风险
```

构建、自动化、原场景验收分别陈述。没有实际标准构建不得声称 Release 构建通过；未完成对应实际验收继续使用中性的 `try`，按现行双语 Commit 规则记录。已知警告区分既有与新增。

采用时分三批落地：

1. **规则。** 统一替换 AGENTS 中“每次最终交付/verify 都全量”的重复触发描述，引用本规范；保留标准构建、实机、公共 API、组件同步和数据保护边界。正式规范集中维护，避免多个文件互相覆盖。
2. **测试质量。** 先修补拖放真实调度与落点缺口，再改写已确认的源码扫描假阳性；逐步完成 117 个条目的审计与风险映射。未完成映射的模块不提前启用局部最终交付免全量。

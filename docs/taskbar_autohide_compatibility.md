# Windows 自动隐藏任务栏与底部 Dock

## 目标与当前状态

保留用户触边、任务栏点击及键盘唤起；避免窗口最小化等被动激活导致任务栏展开并遮住 Dock。
当前候选在首轮诊断基础上增加激活展开过滤。**本机普通窗口经 Dock 最小化的样本已确认
实际执行抑制，并保持任务栏收起**；其余场景仍按下文验收范围分别确认。
保护按底部 Dock 所在显示器及 Windows 实际自动隐藏状态启用，与任务栏外观开关独立；
仅启用保护时，不接管原生任务栏主题。关闭 Dock 或改为其他边缘后取消保护。
`floatingShortcutMode` 仅表示启用召唤快捷键，普通底部 Dock 仍存在，不能据此取消保护。
保留已经删除的光标回推逻辑的删除结果，不新增用户入口，也不改变最小化命令或动画覆盖窗口。

## 已有证据与解释边界

2026-09-17 的原场景日志显示：普通窗口最小化后，前台先转到 `Shell_TrayWnd`，
随后自动隐藏任务栏从屏幕下缘向上移动；当时光标未到屏幕底边。也观察到非 Dock 发起的
最小化出现类似序列。因此强制移开边缘光标无法处理该触发路径。

最大化窗口的 Dock 动画覆盖窗口会覆盖整个显示器；已有日志中它伴随任务栏暂时失去
topmost，任务栏在动画期间保持隐藏。这与 Shell 的全屏避让机制相符，是“最大化最小化
不触发”的高可信解释，但不是所有 Windows 构建的保证，也不能用它代替展开原因过滤。
目前保留该覆盖窗口行为，避免先移除现有保护效果。

参考：[微软关于全屏识别与 NonRudeHWND 的说明](https://devblogs.microsoft.com/oldnewthing/20250522-00/?p=111211)。

## 原生观察器

对本机 x64 `Taskbar.dll` 离线读取微软公开 PDB 并检查反汇编，发现主、副任务栏处理
`WM_ACTIVATE` 时调用各自的 `Unhide(0, 8)`。这个 `8` 是此模块的原生请求值，
不能等同于其他模块（如 `Taskbar.View.dll`）中编号相同的原因枚举。

适配身份为 `Taskbar.pdb` GUID `BC068C70-D2B5-878D-1FBB-AFD6824EC5D2`、age 1，
PE 时间戳 `0x01dffebf`、映像大小 `0x308000`；入口 RVA 为 `0x924c0` 与 `0x14cca8`。
只有身份及入口字节全部匹配才安装 MinHook 观察器。其他构建保留消息观察和系统原行为。
所有不满足过滤条件的展开请求直接调用原函数，保留参数、返回值与焦点处理。
不丢弃 `WM_ACTIVATE`，不抢前台、不移动光标、不事后移动或隐藏任务栏。
该 PDB/ABI 校验是支持范围约束，不是跨 Windows 版本的符号适配方案。

日志前缀为 `[TaskbarAutoHide]`，包括激活前后、原生展开调用、单调时间、调用线程、
任务栏/前台/前窗口句柄、最小化状态、矩形、光标及调用点 RVA。不采集窗口标题或内容。
`adapter flags=1` 表示展开和焦点适配入口全部安装成功；负值表示不支持或安装失败，继续原行为。
`taskbar=0` 表示该次原生调用不在被观察的 `WM_ACTIVATE` 调用栈内，不能据此归属于某个任务栏。
丢失记录会单独计数；没有记录不能证明没有调用。

Explorer 只向固定缓冲区写入，忙或满即丢弃，每线程最多每秒 64 条。宿主定时排空并记录日志。
停用控制器或宿主退出后停采；模块与跳板由现有 TAP 生命周期保留到 Explorer 退出。
内部共享内存协议升级为 v8，宿主和 Hook 必须同时更新并重启 Explorer；不改变组件公共 API。

## 本轮过滤条件与保留主动操作

仅在被保护任务栏已经收起到底边、指针不在该显示器的底边触发区、且没有原生焦点请求
上下文时，过滤激活处理中的 `Unhide(0,8)`。主任务栏调用点固定为 `0x92af3`，副任务栏
为 `0x22550`，都受前述映像身份校验约束。可见或正在展开的任务栏、鼠标点击激活、其他
调用点/原因/参数，以及几何查询失败，均放行。被过滤调用记录为 `suppressed-activation`。

补充键盘实测确认 Win+T/Win+B 等操作也会经过请求 8。因此除展开入口外，适配器还同时
挂接本机 `TaskbarHost::SetFocusOnTaskbar`（RVA `0x84de0`）和
`TaskbarHost::SetFocusWithCommand`（RVA `0x123e30`）。微软 PDB 确认其签名分别为
`void()` 和 `bool(TaskbarCommand, bool)`。这些焦点路径和本模块的任务栏快捷键处理
使用有作用域的在途计数，允许嵌套及同步跨线程调用；离开调用即撤销，不使用统一等待时间。
`focus-enter` / `focus-leave` 和记录中的 `explicitFocus` 用于核对真实调用来源。

第二轮日志说明上述上下文仍不完整，因此新增两个更外层的 `TrayUI` 入口：
`HandleTaskbarHotkey(WPARAM)`（RVA `0xdc860`）和 `_OnFocusMsg(UINT,WPARAM,LPARAM)`
（RVA `0xe7ecc`）。后者在本机模块内处理 `0x55c/0x55d` 焦点消息；非零 `wParam`
请求任务栏焦点，零值归还桌面焦点而不放行展开。六个入口须全部校验并安装成功。
若明确的快捷键/焦点请求到达时主任务栏已是前台且仍隐藏，直接用该在途 `TrayUI` 对象
调用原生 `Unhide(0,8)`，补足不会再次触发 `WM_ACTIVATE` 的情况；不会保存对象指针到调用外。
已显示、未被保护、前台不是主任务栏或几何查询失败时不补发。日志 `explicit-reveal` 记录补发后的矩形，
`protection` 的 flags/request 分别表示实际/请求保护状态。原有光标与激活过滤规则不变。

这是对已检查原生调用路径的区分，不是 Windows 提供的通用“用户意图”标志。新增入口
能否完整覆盖当前构建的键盘操作仍待新候选实测；未知辅助功能、异步焦点路径或程序主动
激活任务栏可能缺少该上下文，不能声称已经覆盖。任一必要 Hook 校验/安装失败即不启用过滤。
主任务栏已取得前台但保持隐藏后的键盘唤起，也须单独验证，不能用规则单测代替。
副任务栏尚未验证连续键盘唤起；主任务栏的补发路径不能据此宣称覆盖副任务栏。

宿主每秒核对一次保护归属，覆盖外部自动隐藏设置和 Dock/显示器变化；此核对不隐藏或移动
任务栏。正常退出同步停用；宿主退出监视器同时撤销过滤，保留跳板以容纳尚未返回的原生调用。

## 验收与后续实现

### e8e1da13 的首轮实机反馈（2026-09-17）

用户反馈：普通窗口经 Dock 最小化概率弹出，经标题栏最小化会弹出；最大化窗口经 Dock
最小化不弹出；主动触边仍会弹出。此结果验证的是诊断候选，尚未验证被动展开过滤。
运行宿主 PID 12972，Explorer 加载的隔离 Hook 与构建输出 SHA256 一致：
`D1B34F254BCECCE1F5A9365AA53CBF6DF0B2F776C51D41FA6EBAC1860494ABB6`。

| 原始观察 | 同次调用内的证据 |
| --- | --- |
| 标题栏最小化，宿主 Trace 2 / 7 | 原生 tick `12951562` / `13020968`：激活值 1，`Unhide(0,8)`，调用点 `0x92af3`；返回前任务栏 top 从 1438 变为 1380 |
| 普通窗口 Dock 最小化，Trace 5 / 6 | 原生 tick `13006953` / `13015218`：同一激活分支和展开位移，光标分别为 `(987,1407)` / `(999,1367)`，屏幕底边为 1440 |
| 最大化后 Dock 最小化，Trace 3 / 8 | 动画覆盖矩形 `[0,0,2560,1440]`；最小化阶段未记录激活展开请求 8，出现的是其他调用点的请求 9；用户报告未弹出 |
| 触边样本 | 光标 y=1439，调用点 `0x91574`，请求 15，与激活请求 8 不同 |

由此可确认当前构建的被动展开至少有一条直接原因：任务栏收到激活后，激活处理函数
同步调用原生展开入口。请求 8 仍不能单独证明非用户主动行为，键盘和辅助功能须另行核对。
激活消息的 `lParam` 在这些记录中全部为空，因此不能以其“前一个窗口”是否最小化作为过滤条件。
Trace 1 的普通 Dock 最小化未记录相同展开调用；不能把概率现象改写为每次必现。

### ec13297c 的第二轮实机证据（2026-09-17）

用户确认完成有序复测；此确认不等于报告各项通过。宿主 PID 17228，Explorer 实际加载的
Hook SHA256 为 `452C5A9E4B0F9DA1D49257993A0E7C26A85290B81BF672E6CDC78E59B7BFF22E`，
与候选输出相同，`adapter flags=1`。tick `14855984` 的普通标题栏最小化仍在请求 8 内
将任务栏 top 从 1438 变为 1380，没有抑制记录，目标验收未通过，已用独立 verify 提交记录。

实际设置 `floatingShortcutMode=true`、`showOnlyWhenSummoned=false`，候选错误地将
“启用召唤快捷键”当成“没有普通底部 Dock”，使保护根本未启用。当前修订改为直接根据
Dock 启用、底部位置和实际自动隐藏状态判断，并沿用 Dock 布局的虚拟桌面坐标映射显示器。
回归测试使用这个真实设置组合，而不是直接将保护条件写死为 true。
键盘 tick `14874812` 带显式上下文，但另一个键盘样本 `14879171` 没有上下文；
这促成了上文两个外层焦点入口的补充，尚待启用保护后的实机验证。

### 107f0f4b 的抑制生效证据（2026-09-17）

用户反馈“好像是抑制成功了”，随后只读核对运行产物和原始日志。当前宿主 PID 16436，
实际加载的隔离 Hook SHA256 为 `72C43286C816A08562AA3ED9F1EEEBAC8AC014954E0221F072FAB78DBB301856`，
与该候选构建产物一致；验证清单中的源码及产物哈希也全部匹配。
`adapter flags=1`，`protection flags=1 request=1`，说明适配安装成功且保护实际启用。

| 本地时间 | 原生 tick | 同次调用证据 |
| --- | --- | --- |
| 19:14:21.611 | 16533359 | 请求 8，显式焦点计数 0，出现 `suppressed-activation`，激活前后任务栏 top 都为 1438 |
| 19:14:50.519 | 16562312 | 同上，光标 `(1001,1367)`，未到屏幕底边 |
| 19:14:51.612 | 16563359 | 再次命中抑制，原生处理返回后仍为隐藏矩形 |
| 19:14:54.688 | 16566406 | 同上，光标 `(1011,1348)` |

这四次记录与宿主 DockTrace 2/3/4 中的普通窗口最小化对应，目标窗口从非最大化状态进入
最小化，前台转入任务栏。任务栏矩形在原生处理返回及后续动画层撤销/轮询时仍为
`[0,1438,2560,1498]`；旧候选相同激活调用会升至 `[0,1380,2560,1440]`。
`suppressed-activation` 只在生产分派跳过原生展开调用后记录，所以该证据确认的是实际
拦截执行及可观察的保持隐藏结果，而非仅根据“这次没弹”作概率判断。

同次宿主的键盘热键 510 在 tick `16528984` 带显式焦点计数 2，原生请求 8 被放行，
任务栏 top 从 1438 变为 1380。这只证明此键盘样本正常，不能替代全部键盘和连续唤起验收。
本次不宣称标题栏路径、全部 Win/Win+T/Win+B 操作、隐藏前台的补发、多屏、退出清理或
其他 Windows 模块版本全部通过。原始证据保存在本地 `feedback-3/`，未向仓库提交运行日志。

在同一候选及同一显示器下分别测试普通窗口的 Dock 最小化、标题栏最小化、最大化后 Dock
最小化、主动触边、Win/Win+T、任务栏点击；多显示器还须覆盖副任务栏。记录操作顺序和现象，
对齐宿主 `DockTaskbarTrace` 与原生 `[TaskbarAutoHide]` 的 tick。

新候选须复测普通/最大化窗口经 Dock 与标题栏最小化、触边、Win/Win+T/Win+B，重点核对
被动样本出现抑制记录时是否确实保持收起，以及键盘请求是否带焦点上下文并能展开。之后补测
关闭所有外观效果、Dock 停用、宿主退出、多屏、触控和辅助功能。若原生入口未调用但仍展开，
再追踪当前特性开关下的 `Taskbar.View.dll` 分支；不能扩展屏蔽未知原因来掩盖漏拦。
只有过滤实测通过，才单独评估给动画窗口增加 `NonRudeHWND`，消除偶然的全屏避让依赖。
构建和自动测试不能代替上述桌面兼容性验收。

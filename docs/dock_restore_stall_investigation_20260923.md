# Dock 最小化后无法恢复：排查记录

日期：2026-09-23。审查源码：`fc9f6ba9`。状态：发现可导致跨线程等待的高风险路径，尚未复现用户故障，未修改生产代码。

以下保留首轮只读排查结论；后续代码候选与实际检查结果见 [恢复流程调整与验证](dock_restore_stall_fix_20260923.md)。

## 现象与证据边界

用户反馈偶发从 Dock 最小化后无法恢复，随后该应用通过 Dock 和 Windows 任务栏均无法恢复。用户目前无法复现，也不记得具体应用。没有故障现场的窗口状态、线程栈或退出 SnowDesktop 前后对照，因此不能将以下代码风险认定为该次故障的已确认根因。

本次只读检查恢复、前台切换、动画清理、最小化回退及相关测试，并保存现有日志。未启动、枚举或操作桌面宿主窗口，未重启 SnowDesktop 或 Explorer。进程列表中的三个 SnowDesktop 进程分别为主程序、`--watch-process-handle` 看护进程和 `--shell-menu-helper`，不能据此判断存在三个桌面宿主。

## 首要风险：输入队列合并后的同步前台切换

生产入口在 [app_dock_window_tracking.cpp](../src/app/app_dock_window_tracking.cpp)：

1. `RequestDockWindowShow`（119 行）先调用 `ShowWindowAsync`。
2. `ActivateDockWindowAfterShow`（155 行）观察最小化状态；需要恢复的窗口只有在 `IsIconic` 清除后才进入前台切换。
3. `ActivateDockWindowForeground`（81 行）先调用一次普通 `SetForegroundWindow`，紧接着检查当前前台窗口。
4. 尚未观察到目标进入前台时，111–115 行将当前线程分别附加到当前前台线程和目标线程，再调用 `SetForegroundWindow`。解除附加依赖局部对象的析构（30–36 行）。

这是一个实际存在的阻塞风险，而不是已复现的现场结论：

- 跨输入队列的前台切换可能异步完成，调用后立即检查前台不匹配，不等于请求已经失败。当前代码会在这一间隙进入附加队列回退。[Microsoft 对异步前台切换的说明](https://devblogs.microsoft.com/oldnewthing/20161118-00/?p=94745)
- 合并输入队列后，前台切换可能同步等待原前台窗口处理失活消息；对方停止处理消息会连带阻塞调用方。Microsoft 给出了与此处相似的“普通前台请求 → 附加队列 → 再次请求”挂起案例。[挂起案例](https://devblogs.microsoft.com/oldnewthing/20080801-00/?p=21393)，[输入队列同步语义](https://devblogs.microsoft.com/oldnewthing/20130607-00/?p=4143)
- 此处仅检查目标根窗口与最后活动弹窗是否被 `IsHungAppWindow` 判为挂起，没有检查随后附加的当前前台窗口。`IsHungAppWindow == FALSE` 也不是后续同步调用必定返回的保证：它依据过去一段时间的消息处理状态，文档描述的内部时间阈值为 5 秒且可能变化。[IsHungAppWindow 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-ishungappwindow)
- 一旦同步调用没有返回，局部对象不会退出作用域，析构中的解除附加不会执行。RAII 能处理正常返回和栈展开，不能为不返回的 Win32 调用提供超时。

该路径可能解释“Dock 操作之后目标也不再正常响应”的连带现象，但有一个重要判别条件：正常恢复路径进入这段代码前，目标已经清除了最小化标志。如果未来现场确认目标始终 `IsIconic == TRUE`，且未进入此前的激活调用，必须另查显示请求、目标线程自身挂起或权限回退，不能仍把这条路径当作唯一解释。

## 超时与回退的保护范围

| 位置 | 实际行为 | 不能保证的事项 |
| --- | --- | --- |
| `dock_window_transition.cpp:1848–1854` | 先执行恢复回调，返回后进入等待显示状态并设置 240 ms 清理期限 | 无法中断回调内的同步阻塞；同一 UI 线程被阻塞时也无法执行动画清理 |
| `app_dock_window_tracking.cpp:239–242` | 确认恢复后，才为置前重试设置 1 秒期限 | 该期限不是单次 Win32 调用超时，也不覆盖恢复前的无限期等待 |
| `dock_window_rules.h:440–443` | 窗口仍最小化且等待恢复时继续观察 | 一个仍泵消息、但始终未恢复的目标可能长期保留观察项；这本身不足以解释任务栏也失效 |
| `app_dock_window_tracking.cpp:128–151` | 异步显示请求被拒绝时，根据挂起检查调用 `DefWindowProcW(SC_RESTORE)`，必要时再调用 `SwitchToThisWindow` | 同步回退仍没有单次调用期限；没有现场返回值，不能确认用户触发了该分支 |
| `dock_platform_helpers.h:596–619` | 最小化优先投递系统命令，失败后依次尝试异步显示和默认窗口过程 | 默认窗口过程回退在 UI 线程直接执行，亦需纳入后续无阻塞设计审查 |

动画对目标设置的是 `DWMWA_TRANSITIONS_FORCEDISABLED`；没有在这条路径直接改写目标恢复位置或将目标永久隐藏。其清理还会等待合成提交，故不能仅凭存在 `Finish()` 或 240 ms 常量声称已保证恢复流程有界。单纯禁用系统动画不足以证明“任务栏也无法恢复”的原因。

## 后续处理与关闭条件

优先改造前台切换：移除 UI 线程上的跨应用输入队列附加，利用现有观察器等待普通前台请求的异步结果，明确尊重系统的前台激活限制。仅增加一次 `IsHungAppWindow` 检查不能消除检查后发生阻塞的竞态。同步权限回退需单独评估隔离与时限，不能简单搬进长期驻留线程后仍把任意外部队列附加到该线程。

同时补充受控、有限量的恢复诊断：请求前后阶段、目标/前台 PID 与 TID、显示命令与返回值、`IsIconic`、挂起状态、placement、观察结束原因。可能阻塞的调用前需要可持久化的阶段记录，不能只依赖同一 UI 线程稍后批量输出。

回归应使用独立测试窗口控制原前台失活处理、目标恢复延迟和先返回后显示的顺序，核对宿主调用及时返回、无输入队列残留、后续任务栏恢复仍可进行；覆盖普通窗口、最大化窗口、最后活动弹窗、提升权限应用和快速反向点击。新用例应证明旧行为在正确业务条件下失败，并复用现有测试目标。桌面 Dock 原场景仍由用户实机验证，最终候选按仓库规则完成标准构建、相应测试和 `try`/`verify` 记录。

下次发生时最有价值的信息是应用名、时间、SnowDesktop 是否也停止响应，以及目标实际最小化状态和线程栈。应先保存日志和现场，再检查正常退出 SnowDesktop 后目标是否恢复；不要先强制结束目标应用而丢失现场。未取得这些证据前，本问题保持“根因待确认”。

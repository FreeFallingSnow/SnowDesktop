# 拖放排查与全场景验收矩阵

排查日期：2026-09-10。范围：宿主拖放代码只读排查，增强现有测试；未修改宿主行为。

## 自动化覆盖的实际边界

测试通过不能等同于 Explorer / Edge 到桌面宿主的完整交互通过。下面分别记录路由契约、实际可调用模块和仍需贯通的宿主链路。

| 测试 | 本轮增强 | 能证明的边界 |
| --- | --- | --- |
| `slot_contract_matrix` | 10 个来源面 × 10 个目标面 × 9 类载荷 × 5 种关系，共 4500 个明确预期；包含非法关系和拒绝组合 | 精确核对重排、文件转移、加入 Dock、分组移动/释放、Lua 引用绑定等操作；预期表独立于生产路由函数 |
| `slot_runtime_contract` | 1000 个来源/目标/载荷/数量组合；同实例身份；160 组外部数量、快捷方式和目录摘要；8 种修饰键组合及释放复位 | 实际 `DragSourceList` 分类、`DragTargetResolver` 与 `DragDropController`；目标容器使用测试替身，不代表各组件实际提交成功 |
| `slot_runtime_contract` | 35 组 OLE Drop 返回状态/效果组合；完成坐标、允许效果、断开后的回调、离开不提交 | 实际 COM 适配器的转发；处理器为替身，没有调用 `DesktopApp::HandleOleDrop` |
| `lua_logical_slot_container` | 1600 组载荷/数量/声明/容量/替换状态；横纵排列边界及提交索引；无效来源和提交失败 | 实际 Lua 槽位容器的接收、命中与提交回调；不代表整个宿主拖入与文件系统操作完成 |
| `virtual_file_drop` | 24 组 CF_HDROP、异步接口、启用状态和 HRESULT 组合 | 实际异步探测，不在悬停阶段读取延迟数据或启动文件操作；保留已有虚拟文件落盘、重名保护和失败清理测试 |
| `url_drop_resource` | 用户提供的花瓣无扩展名 URL、WebP MIME、大小写/参数、HTML 与未知类型响应 | 实际资源类型与文件名决策；测试离线，不请求花瓣，不验证宿主是否启动下载 |

10 个面为：桌面、Dock、集合、文件分类、映射文件夹、集合组、文件组、Lua 槽位、引导组件、外部应用。前 8 个是可构建槽位的目标；引导组件和外部边界也必须进入拒绝/导出测试。

9 类载荷为：桌面文件项、映射目录文件项、外部文件、集合组件、映射文件夹组件、文件源组件、其他组件、集合组标签、文件组标签。跨实例与同实例必须分别验收。

`tests/slot_drop_expectations.h` 保存逐项预期。修改生产规则时应审查产品语义并更新对应预期，不能从生产函数计算“期望值”。新载荷/新目标需要显式扩展表格。

## 已定位的执行链路问题

### DND-01：异步外部文件进入普通组件时没有提交路径

用户实测：资源管理器拖入组件显示复制/移动，松手无操作；拖入空白桌面成功。

`app_ole_drop_session.cpp` 的 `HandleOleDrop` 在来源启用异步能力时跳过 `GetDropPaths` 和引用快照。普通组件分支随后要求非空 `dropPaths` 才执行；通用非文件回退又排除了异步来源。专门的异步分支覆盖空白桌面、Shell 项目交接和 Dock 文件夹弹窗，未贯通普通槽位目标。

因此该问题位于外部数据读取与目标提交之间，不是仅靠增加目标的接收声明就能解决。上述用户现象与该分支吻合；本轮未抓取原始 IDataObject，不能将“所有资源管理器拖放必然异步”当作已验证事实。

代码入口：[OLE 会话](../src/app/app_ole_drop_session.cpp)、[异步探测](../src/virtual_file_drop.cpp)。现有与新增自动测试均未调用宿主这条完整分支，仍是高优先级回归缺口。

### DND-02：网络资源下载入口仅接受桌面目标

`QueueUrlDropDownload` 要求 `preview.targetKind == Desktop`。普通组件中的 URL 回退经 `TryGetNonFileDropPaths`、`HandleUrlContent` 创建 `.url` 文件，没有经过网络资源下载。

用户给出的花瓣地址没有点号扩展名，但 `image/webp` 应识别为图片并补 `.webp`，本轮已加入原始 URL 的离线用例。排查期间，用与宿主相同方式发起的 WinHTTP 请求得到 HTTP 200、`image/webp` 和有效 WebP 内容；另一个 HTTP 客户端得到的 567 不能用来解释宿主必然下载失败。已有 `.url` 的内容也与该回退格式一致。

代码入口：[下载调度](../src/app/app_url_drop_download.cpp)、[内容提取](../src/app/app_drop_data_extraction.cpp)、[资源判定](../src/url_drop_resource.cpp)。若空白桌面也生成链接，还要区分浏览器提供的载荷、异步 Shell 物化、HTTP 失败和替换快捷方式失败，不能直接套用组件目标限制。

### DND-03：连续异步文件操作存在落点缓存覆盖风险

`ExecuteFileBackedDropPlan` 的完成回调把单次落点赋给唯一的 `pendingLandingCache_`。`OnShellFileOperationCompleted` 在其他操作尚未完成时仍执行该回调，而 `ReloadItems` 在有进行中的文件操作时延迟刷新。

两个操作在首次模型刷新前先后完成，后一个缓存会覆盖前一个；文件可能已落盘，但前一个操作的集合归属或插入位置无法按原缓存恢复。此项为代码时序推导，尚未实机复现，不报告为已验证缺陷或已修复。

代码入口：[提交与缓存](../src/app/app_drop_execution.cpp)、[完成消息](../src/app/app_shell_file_operation.cpp)、[延迟刷新](../src/app/app_desktop_reload.cpp)。现有 `desktop_drop_cache` 测试只覆盖缓存规则，未覆盖多个请求完成顺序。

## 后续宿主测试接入点

要自动封住 DND-01/02/03，需要在后续允许修改宿主时提供可注入的边界，直接驱动实际调度代码，不能再写一套“模拟成功流程”替代：

1. IDataObject 格式与异步状态 → 捕获最终选中的目标和真实提交请求，要求每个允许场景只有一个提交或明确拒绝。
2. URL 下载请求/完成 → 注入图片、HTML、网络失败与取消，核对目标、图片文件、快捷方式回退和临时文件生命周期。
3. Shell 请求入队/完成/模型刷新 → 控制两个请求的完成顺序及失败组合，核对每个请求的落点、源归属和保留数据。
4. 文件批次结果 → 注入全部成功、全部失败、部分成功，逐项验证来源清理，不以一个批次布尔值代替逐项结果。

这些接入点会涉及宿主代码，未在本轮只改测试的范围内实施。桌面宿主的实际拖放、视觉和悬浮行为按仓库规则由用户实机验证，不使用桌面自动化绕过。

## GRID-01：空副屏新页的尺寸被临时窗口几何污染

- 评估日期与基线：2026-09-14，`fb56ec6d0ea661236f976cde273d2f55056621d9`。用户明确补充当事人的副屏“完全没内容”；版本号、异常布局文件和关机消息时序尚未取得。以下描述评估时的行为；用户随后要求处理已知问题，调整与验证见本节后面的记录。
- 产品边界：用户确认双屏变单屏后回收空副屏页属于正常行为。撤回初评中将该回收列为缺陷、要求保留离线空页及其网格的建议。正常补页可以使用合理默认网格，不要求恢复已删除空页的自定义尺寸。
- 生产入口：[桌面消息处理](../src/app/app_message_dispatch.cpp)的 `WM_SIZE` 将 `LOWORD(lp)` / `HIWORD(lp)` 写入 `virtualWidth_` / `virtualHeight_`，随后调用 `UpdateLayoutWorkArea`。Microsoft 的 [WM_SIZE 文档](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-size)明确这两个值是窗口客户区宽高；它们不保证与同时枚举出的所有显示器范围一致。此分支也未过滤最小化或零尺寸通知。是否在当事人的关机过程中收到过相关中间状态，仍待实机证据。
- 产生异常：[UpdateLayoutWorkArea](../src/app/app_grid_drag.cpp) 按上述宽高裁剪每台显示器的工作区。如果新枚举已包含副屏，而窗口宽度还只有主屏宽度，右侧副屏会被裁成零宽。`ConfigureGridPage` 将该新页算成至少 4 列、3 行；[PadPagesToMonitorCount](../src/app/app_page_grid.cpp) 随即把这组临时计算值写入保存尺寸表。
- 持续存在：后续正确的显示器范围可以恢复工作区，但 `UpdateLayoutWorkArea` 会保留已有行列数，`ApplySavedGridDimensions` 也优先使用保存值，临时网格不会自动重新初始化。[SaveLayoutSlots](../src/app/app_layout.cpp) 再把它写入布局。常规文件刷新和正常退出均可触发保存，不要求关机本身完成某个特定保存回调。
- 受控复现：使用有完整合法尺寸的双页布局，主屏只有一个普通文件，副屏无文件、无组件、无溢出页。先模拟仅主屏在线，正常删除空副屏页；再令枚举返回两台 1920×1080 显示器，但传入的窗口宽度仍为 1920。新副屏成为 4×9；将窗口宽度改为 3840 后仍为 4×9，页面序列化、重新解析和新实例加载后仍为 4×9。临时窗口为 1×1 时，同一路径得到并保留 4×3。
- 对照：相同初始布局和空页回收流程下，接屏时窗口范围与显示器范围一致，新页正常得到 20×9；已有 20×10 页面未被回收时，同样的小窗口输入不会把行列数缩小。缺陷集中在尚无保存尺寸的新页接受了无效或局部几何，不是所有缩放都会损坏配置。
- 精确 1×1 的边界：当前默认配置函数和 `v1.0.5.0` 对应代码都有 4×3 下限，所以本链确认的是“类似的不正常网格”，没有在真正空副屏条件下重现精确 1×1。首次无布局的 Windows 网格导入有独立入口，但已有页面的布局不满足其初始化条件。另一个可产生精确 1×1 的路径记为 GRID-02，不能混作本反馈的解释。
- 关联测试：`dock_and_window_rules` 的默认网格计数、拓扑刷新动作、分页导航和隐藏页集合用例，不覆盖“窗口范围与显示器枚举不一致→新页尺寸登记→正确范围恢复→保存重载”。`application_data_lifecycle` 的布局解析也不能替代宿主补页顺序验证。此次仅审阅相关用例，没有声称完整评估全部测试。
- 建议修复方向：保持正常空页清理规则；区分窗口渲染尺寸与显示器布局范围，验证枚举工作区及其与虚拟桌面范围的一致性后，再为新页登记正式尺寸。对中间状态保留重试能力，避免把零宽、零高或被截断的范围固化为用户配置；合法手动 1×1 应继续保留。
- 关闭条件：贯通消息/几何输入、新页尺寸登记、保存和重载的回归，并验证短暂无效、部分范围、稳定重连及手动网格设置；当事人的原始异常文件或断屏/关机实测用于确认线上反馈归因。当前仅完成受控数据流重现，没有操作真实桌面宿主验证时序。

## GRID-02：启动阶段普通图标页被误判为空后写成 1×1

- 生产顺序：[启动流程](../src/app/app_run.cpp) 先 `LoadLayoutSlots`，再 `UpdateLayoutWorkArea`，稍后才 `ReloadItems(false)`。此时普通图标的位置已在 `layoutRecords_`，但 `items_` 尚未枚举；`PageHasContent` 只看 `items_` 和 `widgets_`，没有考虑这些待恢复位置记录。
- 受控复现：合法双页输入，主副页均有一个普通文件，副页尺寸为 20×10；以只有主屏在线的状态冷启动。首次映射把尚未加载文件的副页误判为空并删除其尺寸，但位置记录仍在。`LoadDesktopItems` 的恢复分支随后恢复副页文件；`ReloadItems` 对不可见页直接继续，没有补回尺寸，也没有把已有非空页 ID 当作待安置项目。
- 保存与重载：[SaveLayoutSlots](../src/app/app_layout.cpp) 在准备文件记录时调用 `RememberSavedPageId`，将文件引用的副页 ID 加回保存列表；该页既不可见又无尺寸，序列化将两个 0 钳制成 1。探针生成了含副页文件、尺寸为 1×1 的有效 JSON，再用真实解析器加载，并在双屏状态映射后得到副屏 1×1。整个输入链没有手工删除尺寸表条目来构造故障。
- 对照与边界：同一份普通图标输入，若在首次页面整理前先恢复文件，副页维持 20×10。该顺序对照只在隔离探针中执行，生产代码未改。用户明确本次反馈副屏完全为空，因此本问题单独记录，不能声称已解释该用户的精确 1×1。
- 建议修复方向：在桌面内容尚未恢复时避免以空的运行时集合判定真实空页，确保清理依据与布局加载阶段一致；同时保证重新登记的页面具有有效尺寸。不能为此取消真实空页清理，或只用最小值兜底掩盖位置记录与尺寸表失配。
- 关闭条件：覆盖离线普通图标页、真正空页、被删除的文件、含组件页及启动时后续页面重排，验证页面/尺寸/内容的一致性和保存重载结果，再完成对应实机场景验收。

# 声明式文字布局复用验证

验证对象：`19db2186`，测试警告调整 `c6c9ddad`。2026-09-06，基线为
`3f9c41c5` 对应宿主 PID 19416，新构建实际宿主 PID 45100。

## 本轮范围

检查唱片逐帧重建路径时，发现通用声明式文字分支每次绘制均创建 DirectWrite
布局，重新设置排版并测量文字。此次复用输入未变的布局，颜色、透明度、坐标、
图标居中与动画仍在每次绘制时应用。微软文档也说明，重复使用布局可避免反复
计算字形位置，见 [Direct2D 与 DirectWrite 文字渲染](https://learn.microsoft.com/en-us/windows/win32/direct2d/direct2d-and-directwrite)。

缓存按组件、surface、节点键隔离，一键只保留一份布局；字体对象、文字、locale、
宽高及排版参数参与精确匹配。字体对象保持强引用，避免地址复用造成错误命中。
最多 128 项、64 KiB 输入数据，单条文本最多 2048 个 UTF-16 码元；超限直接创建。
隐藏、卸载、重载、设备切换及辅助 surface 关闭时清理相应缓存。
输入数据上限不等于 DirectWrite、字体或进程总内存上限。

公共 Lua API 和组件包未变，新增诊断指标口径见
[性能调试工具](performance_debugging.md)。此次没有减少 Lua view 重建或合成提交
次数，也没有把唱片改为独立合成动画。现有 transition 是有限时长插值，将其用于
持续旋转还需解决角度回绕、暂停状态同步及数据更新与原生帧合并的问题。

## 真实耦合播放

音乐实例 `widget-133060937-33` 与频谱等组件共同运行。每个版本两轮，每轮约
10 秒 trace（不启用 ScopeCpu），随后关闭探针，外部读取约 10 秒进程 CPU。
程序在标准构建时重启，完整测试结束后才恢复；新采集前后系统媒体状态为 Playing。

音乐每次原生视图绘制经过时间减少约 80.2%、82.1%，动画仍约 60 Hz。这里使用
`widget.view/draw` 的 inclusive wall，包含新增的布局创建子作用域，以免把新增
分段导致的 self 减少误当成优化。新窗口每次音乐绘制五次布局请求，全部命中；
全体实例缓存稳定为 10 项、654 字节输入数据，未测算这些布局的完整 COM 内存。
背景缓存估算仍为 743436 字节，共享包图片解码数据仍为 12583536 字节。

基线两轮和新版第二轮无 desktop 作用域；新版第一轮记录 2 次 paint、3 次
overlays，不用于声称稳定进程 CPU 收益。用户此前说明额外桌面刷新来自操作，
本轮也不据此判断自动刷新缺陷。

**局部绘制收益明确，总 CPU 收益尚未证实。** 新版两轮关闭探针的 CPU 都高于
基线，不能据此宣称总 CPU 下降，也不能仅以“波动”排除进程级回归。GPU 基本
持平。两版本不是固定曲目、同一进程内交替 A/B，进程 CPU 也包含共享服务及
其他线程；原生视图经过时间不是精确 CPU 时间或 GPU 执行时间。私有提交因
跨进程、运行时长和内容不同而不可直接归因，仍不宣称内存优化或无泄漏。

## 同进程固定输入对照

为核实缓存自身成本，临时诊断程序复用已提交测试中的 DirectWrite 构造夹具，
用五段不变文字交替执行直接创建与缓存命中。每组 5000 帧、25000 次布局请求
及 GetMetrics，丢弃一组预热，保留三组。

| 计时循环中位值 | 直接创建 | 缓存命中 |
|---|---:|---:|
| wall ms | 328.033 | 1.1983 |
| 当前线程周期数 | 898588546 | 3489488 |

固定输入对照确认重复排版成本被省去。该基准不含 Lua 执行、视图解析、GPU 绘制、
共享服务或进程总 CPU；线程周期也不能换算为固定 CPU 毫秒。输入完全不变，
不能将此差值外推到持续变字或频繁调整排版的组件。
